## When to Use This Skill

- The scheduled Monday-morning weekly status job triggers (D17)
- A user asks "give me this week's status email" / "draft the weekly update"
- The TPM specialist is invoked for a multi-release status rollup
- "Publish this week's status to Confluence" — same content, Confluence renderer (D15d)

## Quick Start

```
Input: {
  productIds: ['ndb'],
  asOfDate: '2026-05-19',  // typically today
  sinceWeek: '2026-W20',   // last week boundary
  outputSurface: 'email' | 'confluence' | 'chat'
}

Output: 3-tier HTML email (or storage XML for Confluence) with:
  Top tier — Release-level RAG roll-up
  Middle tier — Per-team weekly delta
  Bottom tier — Standout FEAT callouts

Procedure:
1. Resolve active releases (status: active, per D13) for the active products.
2. In parallel:
     A. statusService.releaseRagByActive(productIds)
     B. statusService.teamWeeklyDelta(teams, { sinceWeek })
     C. statusService.featCallouts(features, { sinceWeek })
3. Compose 3-tier structure.
4. Render charts via chartService for any RAG-over-time / predictability inline.
5. Apply email-broad-leadership renderer (multi-section with anchors).
6. Cite every claim.
7. Preview before send (unless pre-authorised scheduled job).
```

## Core Rules

1. **Fixed 3-tier structure** (D17). Release-level top, team-level middle,
   FEAT-level callouts bottom. Don't introduce a 4th tier or collapse to 2.
2. **Broad-leadership audience** — multi-section with anchor links so VPs
   jump to top tier, EMs jump to their team's row in middle tier, FEAT
   owners jump to their callouts in bottom tier.
3. **Citation on every status claim** (D10). Use the citation form
   appropriate to the recipient context (full URLs for email; JIRA links
   for chat).
4. **Only `active` releases in the top tier** (D13). Planning / shipped /
   archived releases are excluded unless the user explicitly overrides.
5. **Team-weekly-delta sources GitHub + JIRA** — what shipped (commits
   merged via `githubConnector`) + what's at risk (status + dates via
   `jiraConnector`).
6. **Standout FEAT callouts only** — bottom tier is NOT every FEAT, just
   those whose status changed this week (RAG transitioned, gate hit,
   date slipped >2 days, etc.).
7. **One canonical payload, multiple renderers** (D15d). The same payload
   generates the email, the Confluence page, and a chat preview.
8. **Last-refreshed timestamp** on every published artefact (D11).
9. **Inline-CSS HTML**, max 800px, no external assets (per email
   compatibility rule in `documentation-consistency.mdc`).
10. **Preview before send** — unless this is the pre-authorised Monday
    cron job. Even then, the Portfolio Manager can opt into "preview mode"
    per release.

## Quality Validation

- [ ] All three tiers are present (no skipping)
- [ ] Only `status: active` releases in top tier
- [ ] Each team in middle tier has at least one citation (commit OR ticket)
- [ ] FEAT callouts are filtered to status-changed-this-week
- [ ] Total length ≤ 1 screen for top tier (VPs read just that)
- [ ] Anchor links present (`#release-rollup`, `#team-status`, `#feat-callouts`)
- [ ] Inline-CSS HTML, no external assets
- [ ] Confluence variant runs `confluence-width-cleanup` before push (D15d, D17)
- [ ] Last-refreshed footer present
- [ ] Audience declaration: `audience: broad_leadership` (multi-section)

## Common Mistakes to Avoid

- Including planning or shipped releases in the top tier
- Listing every FEAT instead of only the standouts
- Forgetting the anchor links (audience-specific reading flow breaks)
- Forgetting the last-refreshed timestamp
- Pushing the Confluence variant without running width-cleanup
- Sending without preview when not pre-authorised
