01 · Project Lighthouse

How we built the NDB delivery framework — and how it runs every week.

Mission: honest, usable operational truth with ownership on the person who can act.

Vision: Shine the problem → Suggest the fix → Fix under HITL.

The operating system: gate-train SDLC, Delivery Ops surfaces, weekly NDB Ops KPI rhythm (OnCalls, CFD/CFI), automated EM reminders, and clear RACI.

02 · What Project Lighthouse is

One operating system for NDB delivery — so leaders decide, not assemble status.

If you are new here: we did not add another status deck. We wired four capabilities that already run the org’s release work into one place.

1 · Trust the numbers

  • JIRA stays the single source of truth
  • We fixed hygiene at the board (not in slides)
  • Every count opens the real ticket list
  • No “trust me” spreadsheets

2 · Run the release train

  • Shared calendar: planning → ship
  • Named gates everyone recognizes
  • Hotfixes use a shorter path
  • Same UI for every release type

3 · Pulse every week

  • Standing NDB Ops weekly review
  • OnCalls & customer defects first
  • Then blockers, quality, security
  • Engineering Managers get auto-nudges

4 · Assist, then act safely

  • AI drafts briefs from live data
  • Suggestions always show the source
  • A human approves before any write
  • Never invents ticket IDs

05 · What was not working

Fog = broken truth + wrong RACI + no weekly scoreboard.

Broken truth

  • Inconsistent fields — Status / FixVersion / Component / Type
  • Resolved treated as done (it is TBV)
  • 17+ apps / Slack / Excel for one story
  • Capacity workbook with `#REF!` cells
  • OnCalls / CFDs invisible until someone asked

Broken operating rhythm

  • TPM assembled narrative FEAT should own
  • EMs not nudged on stale / open queues
  • No standing weekly KPI pulse for Ops
  • Partners couldn’t see NDB asks
  • Gate slips without named owner
If OnCalls and CFDs only surface in a fire drill, the framework failed. Weekly Ops exists so those numbers are routine — not exceptional.

08 · Automated reminders for EMs

Nagging is a system job. Judgment stays with the EM.

What we automated

  • Generic Emailer: JQL → table → SMTP
  • Schedules: day · hour · minute · timezone
  • Recipients + optional project-team expand
  • Email History audit (generic-reminder type)
  • Same pattern for weekly / recurring EM nudges

What EMs still own

  • Act on the queue (close, defer, reassign)
  • Say/do and sprint hygiene
  • Capacity / commit honesty for their team
  • Respond to partner dependency asks
  • Risk Indicator when Yellow/Red on their FEATs
